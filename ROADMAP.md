# Roadmap

Список планируемых улучшений с приоритетами. Реализованные пункты помечаются
ссылкой на коммит. Пункты упорядочены внутри секции по предполагаемой пользе
для большинства пользователей.

Обозначения статуса:
- ⏳ — запланировано
- 🚧 — в работе
- ✅ — реализовано (с указанием версии или коммита)
- ❌ — отклонено (с обоснованием)

---

## v2.1 — устойчивость и автоматизация

Близкая итерация. Цель: закрыть оставшиеся недоделки из аудита и сделать
скрипт удобнее для CI/Ansible-сценариев.

### Корректность и UX
- ⏳ Допуск повторного запуска `do_full_install` после прерванной первой
  установки
- ⏳ `validate_ip` принимает только октеты 0–255 и проверяет маску /0–32
- ⏳ Валидация всех аргументов CLI `instance create` (порт, имя, пути)
- ⏳ Единый `confirm` helper вместо разных Y/n vs y/N
- ⏳ Поддержка `NO_COLOR=1` и автоопределение non-tty
- ⏳ Подтверждение деструктивных операций унифицировано (имя инстанса
  везде, `DELETE` только для full-uninstall)
- ⏳ Единый `log_to_file` в `/var/log/1c-crserver/manager.log` для аудита
  действий

### Автоматизация
- ⏳ Bash-completion для всех CLI-команд
- ⏳ `instance list --json` для интеграции с Ansible/мониторингом
- ⏳ `crserver healthcheck [-i name]` — exit-код для systemd `ExecStartPost`
  и мониторинга
- ⏳ Dry-run (`--dry-run`) для всех деструктивных операций
- ⏳ shellcheck-чистота скрипта (с CI-проверкой)

### Бэкапы
- ⏳ Ротация по числу копий, а не только по дням (`--keep-last N`)
- ⏳ `crserver backup verify <архив>` — отдельная команда верификации
- ⏳ Прогресс-бар через `pv` (опционально, если установлен)

## v2.2 — расширение возможностей

Новые функции, требующие более серьёзной работы.

### Бэкапы
- ⏳ Шифрование (`--encrypt` через `gpg --symmetric` или `age`)
- ⏳ Удалённый бэкап (S3 через `aws-cli`/`mc`, SFTP, rsync на удалённый хост)
- ⏳ Инкрементальные бэкапы через `tar --listed-incremental`

### Инстансы и хранилища
- ⏳ `crserver instance clone <src> <dst>` — копирование инстанса с переименованием
- ⏳ `crserver instance export <name>` / `import <archive>` — переезд между
  серверами одним архивом (конфиг + данные)
- ⏳ Управление списком пользователей хранилища (если crserver предоставит
  CLI-интерфейс к `1cv8wsrv.lst`)
- ⏳ Поддержка PostgreSQL-backed хранилищ (`-srvr`-режим crserver) — для
  крупных инсталляций

### Файрвол
- ⏳ Поддержка `nftables` (Debian 12 default)
- ⏳ IPv6 (отдельные `ip6tables` правила)
- ⏳ Интеграция с `fail2ban`-jail для портов crserver

### Мониторинг
- ⏳ Prometheus textfile exporter (`/var/lib/node_exporter/textfile/crserver.prom`)
  с числом активных подключений и статусами инстансов
- ⏳ Уведомления (Telegram/Slack/email) при failed-бэкапе и
  `Restart=on-failure` срабатывании
- ⏳ Аудит входов в хранилища через парсинг journalctl

## v3.0 — большие изменения

Долгосрочные задачи, требующие отдельного дизайна.

### systemd
- ⏳ Запуск `crserver` напрямую (`User=`/`Environment=`) без обёртки
  `/bin/sh -c` — корректный MainPID для journald
- ⏳ `ProtectSystem=strict` + динамически генерируемые `ReadWritePaths=`
- ⏳ systemd-таймеры вместо cron для бэкапов

### Безопасность
- ⏳ Подпись релизов скрипта (PGP или sigstore) с проверкой в `do_self_update`
- ⏳ Хеш-сумма ожидаемой версии в репозитории
- ⏳ Hardening systemd-юнита (`SystemCallFilter=`, `CapabilityBoundingSet=`)

### Документация и инфраструктура
- ⏳ Перевод README на английский для GitHub-видимости
- ⏳ asciinema-демо установки и миграции v1→v2
- ⏳ Тесты на bats или smoke-тесты в Docker (debian:12)
- ⏳ GitHub Actions: shellcheck + smoke-тест

### TUI/Web
- ⏳ Опциональный TUI через `dialog`/`whiptail` для удалённой работы
- ⏳ Web-UI (опциональный, на отдельный issue) — отдельный проект-обёртка

## Отклонённые предложения

Пункты, рассмотренные и отклонённые с обоснованием.

- ❌ **Подпись через self-signed cert + custom CA для self-update.**
  Вводит сложную обработку ошибок без существенного роста безопасности
  относительно подписи через PGP/sigstore. Лучше реализовать сразу
  стандартный подход.

## Как добавить пункт

1. Открыть PR/issue с предложением.
2. Описать use case в одном-двух предложениях.
3. Поставить статус ⏳ и положить в подходящую секцию (v2.1 / v2.2 / v3.0).
4. При реализации обновить статус на ✅ с указанием версии или хеша коммита.
